# Occupant Schedule Generator — Project Spec

**Owner:** Stella Samosir
**Status:** v1 planning
**One-line pitch:** A browser tool that turns annual daylight results into realistic, stochastic occupant schedules, so energy simulations reflect variable human behavior instead of one fixed schedule.

---

## 1. Why this exists

Energy simulations usually assume one fixed schedule (e.g. Sveby or ASHRAE profiles). Real occupants arrive at different times, leave for breaks, and switch lights on depending on how dark the room feels. This is a major cause of the performance gap between predicted and measured energy use.

This tool uses **published, validated stochastic models** to generate many plausible occupant behaviors from daylight data. It then shows the *spread* of lighting energy use compared to the standard fixed schedule.

**Key principle:** AI builds the system. It does not invent the behavior. All behavior comes from cited models running on a seeded random number generator, so every result is reproducible and defensible.

## 2. Research question

> For a given office zone and daylight condition, how much does lighting energy use vary between realistic stochastic occupants, and how does that range compare to the standard fixed schedule?

## 3. Scope

### v1 (build first)
- One office zone, one occupant per run
- Hourly timestep (8760 h)
- Lighting behavior only
- Three cases compared:
  1. **Fixed schedule:** standard profile (Sveby office values, supplied by Stella)
  2. **Deterministic threshold:** lights on when occupied AND illuminance < setpoint (e.g. 300 or 500 lx, user-set)
  3. **Stochastic:** presence model + illuminance-based switching probabilities

### v2 (later)
- Manual blinds model (Haldi & Robinson / Reinhart Lightswitch-2002)
- Sub-hourly timestep
- Multiple sensor points / multiple occupants per zone
- Dimming control comparison

### Out of scope
- Running EnergyPlus inside the tool (schedules are exported to Honeybee instead)
- Any behavior generated by an LLM

## 4. Models (to be verified against original papers before coding)

| Behavior | Model | Source |
|---|---|---|
| Presence (arrivals, departures, breaks) | Inhomogeneous Markov chain from an hourly presence-probability profile + mobility parameter | Page, Robinson, Morel & Scartezzini (2008), *Energy and Buildings* |
| Switch-on at arrival | Logistic probability vs. work-plane illuminance | Hunt (1979); refit in Reinhart (2004), Lightswitch-2002, *Solar Energy* |
| Intermediate switch-on (while present) | Small probability when illuminance is low | Reinhart (2004) |
| Switch-off at departure | Probability depends on expected absence length | Pigg, Eilers & Reed (1996); used in Reinhart (2004) |

**Rule:** Stella supplies and verifies all coefficients from the original papers. No coefficient is hardcoded from memory. Each formula in the code cites its paper and equation number.

## 5. Inputs

- **Illuminance CSV:** 8760 rows, one column, work-plane illuminance in lux. Exported from Climate Studio or Honeybee annual daylight. Use one sensor point or the zone average, and preprocess to a single column.
- **Presence profile:** 24 hourly presence probabilities (weekday), plus weekend handling.
- **Model coefficients:** from the papers in section 4.
- **Settings:** number of occupants (default 100), random seed, illuminance setpoint for the deterministic case, lighting power density (W/m²), floor area.
- **Fixed schedule:** Sveby office lighting/occupancy values (supplied by Stella).

## 6. Outputs

- Schedule CSVs (8760 rows, 0/1 or fraction) for each occupant, in a format usable by Honeybee / EnergyPlus `Schedule:File`
- Summary table: annual lighting on-hours and kWh/m² per case
- Histogram of stochastic results with the fixed and deterministic cases marked as lines
- Statistics: mean, median, P10, P90, min, max
- Run metadata: seed, coefficients and settings used (for reproducibility)

## 7. Lighting energy estimate (in-tool)

Annual lighting energy (kWh/m²) = LPD (W/m²) × annual on-hours / 1000

This is a fast first-order comparison. Full heating/cooling interaction is checked afterwards by running the exported schedules in Honeybee.

## 8. Validation

- Known-answer tests: switch-on probability at fixed illuminance values matches values computed by hand from the paper's equation
- Same seed gives identical output
- Presence model: simulated hourly presence frequencies converge to the input profile over many runs
- Sanity checks: lights never on when absent; stochastic mean is plausible relative to the deterministic case
