# CLAUDE.md — Occupant Schedule Generator

Read PROJECT_SPEC.md before starting any task. It is the source of truth for scope, models and milestones.

## What this project is
A single-page browser tool that generates stochastic occupant lighting schedules from annual work-plane illuminance data, using published occupant behavior models. The output is used in building energy simulation research (Honeybee / EnergyPlus).

## About the user
Stella is a building energy and LCA specialist (MSc, Lund University). She knows building physics and simulation well, but is still learning to code. Explain code decisions in plain language. Explain domain topics only if she asks.

## Tech rules
- One self-contained `index.html` with HTML, CSS and vanilla JavaScript. No frameworks, no build step, no backend.
- Charts: Chart.js 4.4.1 loaded from cdnjs (`chart.umd.js`, already minified in v4). Ask before adding any other library.
- All randomness goes through ONE seeded PRNG (e.g. mulberry32). Never use `Math.random()`.
- Same inputs + same seed must give identical outputs.
- Metric units only. Illuminance in lux, power in W/m², energy in kWh/m².
- Numbers shown SI-style: thin-space thousands, point decimal ("3 325 lx", "12.5 lx"). Never comma grouping.
- Must work on phone width as well as desktop.

## Code structure inside index.html
The script is split into numbered sections: 1 constants, 2 data functions, 3 random numbers, 4 presence model (Page et al. 2008), 5 lighting switching model (Reinhart 2004, Hunt 1979), 6 comparison cases, decomposition and energy, 7 export (CSV, metadata, ZIP writer), 8 UI, 9 charts, 10 event wiring, 11 test panel. Sections 2–7 are pure functions. Energy settings (setpoint, LPD, floor area) are post-processing: they update the page instantly without re-running the model. Model logic added in later milestones goes in its own pure-function section before UI. UI code may call pure functions; pure functions never touch the DOM.

## Random numbers
- Only `mulberry32` (section 3). Each occupant has a separate stream per process: `streamSeed(seed, occupant, STREAM.presence | STREAM.lighting | STREAM.userType)`. Changing the lighting model never changes presence, and occupant k is the same for any N.
- Presence draws one random number every hour; lighting draws two every hour (switch-on, switch-off); user type draws one per occupant. Always drawn, needed or not, to keep streams aligned.
- User types and lighting streams are shared across μ values, so μ comparisons differ only through presence.

## Numerical helpers
- erf: Abramowitz & Stegun (1964) formula 7.1.26, cited in the code, verified against exact erf. Any other numerical approximation must be cited the same way and tested against exact values.

## Scientific integrity rules (most important)
- Never invent model coefficients or recall them from memory. If a coefficient is missing, stop and ask Stella for the value from the paper.
- Every formula in the code gets a comment with: paper, year, equation number.
- Never generate occupant behavior with an LLM or with hand-written "plausible" patterns. Behavior comes only from the models in PROJECT_SPEC.md.
- Keep model logic in pure functions, separate from UI code, so they can be tested.
- Flag any assumption you make in a `// ASSUMPTION:` comment and mention it in your reply.
- Data-quality heuristics (e.g. timing and unit checks) are not model coefficients, but their thresholds are still marked `// ASSUMPTION:`.

## Input conventions (decided in milestone 1)
- Illuminance CSV: one column, exactly 8760 values, one optional text header row. Decimal comma accepted (Swedish Excel).
- Rejected with a clear message: wrong row count (8784 flagged as leap year), text or negative values, blank lines inside the data, more than one column (semicolon, tab, two or more commas, or a comma file whose numbers count up as an hour index).
- ASSUMPTION: row i (0-based) = hour interval starting (i % 24):00 on day floor(i / 24), non-leap year from 1 Jan 00:00. Checked on Stella's Grasshopper export (2026-10-19): the daily light centre follows standard-time (CET) solar noon within +0.1 to +0.3 h all year and does not jump at the daylight-saving dates, so the rows are in standard time and aligned to within the hour. EnergyPlus Schedule:File alignment is still confirmed in milestone 6.
- Working hours for preview statistics: 08:00–17:00 (intervals starting 08…16), all 365 days until the presence model adds weekday handling in milestone 2.

## Testing
- No separate `tests.html`. The test panel lives inside `index.html` and is shown only when the page is opened with `?test` in the URL (e.g. `index.html?test`). This keeps one file and makes sure tests always run the real code.
- Tests are known-answer tests on the pure functions, using inputs whose results can be checked by hand. Each test name states the expected value.
- `test-data/` holds synthetic CSVs (generated by `test-data/make_test_data.py`, fixed seed) for manual upload checks. They are not real daylight results and contain no occupant behavior.

## Time convention
- All files in standard time (UTC+1). With EU summer time on (default), the presence profile and the Sveby window follow clock time, i.e. 1 h earlier in standard time from the last Sunday of March to the last Sunday of October (`summerTimeRange`, `clockIndex`). Illuminance is never shifted. Presence validation and hour-of-day charts are in clock time.

## Daylight input (case study)
- `daylight/simulate_reinhart_office.py` (honeybee-radiance + Radiance 6.0a via pyradiance) produces the case-study illuminance. Model set-up and checks are in `daylight/README.md` and `daylight/output/daylight_metadata.json`. Do not tune the geometry to hit a target daylight factor; report gaps instead.

## Export
- No ZIP library: `makeZip` writes stored entries per PKWARE APPNOTE with CRC-32. Any change must keep the ZIP round-trip test passing and be checked once with an external reader (Python `zipfile`).
- Every export carries `metadata.json` with seed, settings, coefficients with sources, assumptions and the input file's CRC-32.

## Outputs
- Schedule CSVs as defined in PROJECT_SPEC.md section 6: per occupant a lighting (0/1) and an occupancy (0/1) schedule, 8760 rows, one column per occupant, for EnergyPlus/Honeybee, IES VE and IDA ICE. The optional averaged fractional schedule must always be labelled as an average.
- Every export includes a metadata file listing seed, coefficients, settings and date.
